# 评估有效性与置信度路径复核

日期：2026-11-18。本轮根据用户提交的六项结论补充统计及分项对照。没有修改业务实现，原有审计报告保留为历史记录。

## 结论

六项意见的主要方向成立。评测独立性应升为阻断对外效果结论的问题，不能仅列为一般的“过拟合风险”。当前满分只能作为同源、已调优合成基准上的观察，不能作为未知问题上的泛化或复杂方法优越性的证据。

需要精确区分：测得的分数可以复现，不等于它是独立测试成绩；词典与问题高度重合，也不能单凭词频还原规则编写的时间顺序或开发者动机。本次进一步做了分项对照，直接检验现有基准上的增益来源。

## 1. 词典与题集耦合：确认；22/23 对应包含改写的口径

词典共有 23 个触发词。按实际代码的触发规则重新统计：

| 统计范围 | 文本数 | 不同触发词覆盖数 | 实际产生扩展的问题数 |
| --- | ---: | ---: | ---: |
| 合成集 question 主字段 | 40 | 20/23 | 11/40 |
| 主问题及 paraphrase_variants | 120 | 22/23 | 本列未按该范围统计 |
| python_support 测试集主问题 | 13 | 0/23 | 0/13 |

40 个主问题中未出现的触发词为 delete、outage、payment；把改写一起计入后，仅 delete 未出现。用户的 22/23 统计在包含改写时成立，不能解释成主评测运行时有 22 道题被扩展。当前评测器实际遍历的是 question 主字段。

Python 资料上不触发说明词典缺乏该领域覆盖，并非规则扩展方法本身无效的证据。领域词典也可以是合理工程设计；问题是规则、阈值和参数若根据已看过的测试问题反复修改，就不能继续把同一批题标成独立测试。

## 2. 补充的分项对照：满分主要由规则扩展推动

保持当前 65 篇合成文档、40 道问题、父子分块、SVD embedding、特征重排和阈值一致；关闭答案缓存。

| 配置 | Recall@5 | MRR | NDCG@5 |
| --- | ---: | ---: | ---: |
| 原第六组基线 | 0.9706 | 0.9338 | 0.9362 |
| 仅开启规则查询扩展 | 1.0000 | 1.0000 | 0.9885 |
| 仅开启共现图检索 | 0.9706 | 0.9338 | 0.9370 |
| 全部开关开启，但把扩展器替换为恒等函数 | 0.9706 | 0.9338 | 0.9370 |
| 全部新特性开启 | 1.0000 | 1.0000 | 0.9917 |

因此，在这套基准上，单独使用规则扩展就足以达到 Recall@5 和 MRR 满分。没有证据把这两项满分主要归因于图方法或 CRAG。完整组合相对规则扩展的 NDCG 差为 0.0032，本轮没有证明这点差异在未知问题上稳定或统计显著。

这是对现有基准的诊断性归因，不是一套新的独立验证。不能用此次消融再次包装成“方法泛化已证实”。

## 3. AutoRAG 复用评测集选参数：确认

当前 /autorag/tune 读取 cfg.golden_qa_path，与默认架构评测使用同一文件，针对其中可回答的题目选择 RRF 参数；没有显式的开发/测试角色约束。

调参使用有标签的开发集是正常流程；将选择参数所用题集上的最佳分数当作最终测试成绩才是问题。需要：

- 显式区分开发集和最终测试集，调参和阈值校准只访问开发集。
- 在接触新测试集前冻结规则词典、模型、索引配置、超参数和代码版本。
- 保存词典来源、数据哈希、试验记录与选择准则。
- 最终在未用于修改这些配置的问题上报告结果；同一问题的近似改写不要随意分到两边。

RAG 索引包含能回答测试问题的知识文档，本身不是测试泄漏；它是正常的检索设置。这里需要隔离的是测试问题、标签对规则、参数和阈值的反馈。

现有 python_support 已有 dev/test 文件，但样本很少且题目由实施代理编写；不能只改文件名就把旧的同源成绩变成独立验证。

## 4. CRAG 的 INCORRECT 没有驱动拒答：确认

该问题已在 [新增功能接入审查](07_NEW_FEATURES_REVIEW.md) 复现：crag_status=INCORRECT，confidence=0.505，refused=false。

当前最终分支没有消费 INCORRECT 的路由动作。因此“INCORRECT 直接拒答”的文档契约没有成立。应统一路由决策与执行动作，增加包含部分已知词、部分 OOV 的反例测试，而不只测试完全未知问题。

## 5. 置信度覆盖：问题成立，但最终证据分数不一定全部相同

融合后确实把全部候选的 confidence_score 设为 orig_max_conf。本次查询观察到，重排前所有候选均为 0.464140。

不过重排器仍会修改候选分数。实际返回的五条证据为：

```text
0.4641, 0.3182, 0.4449, 0.2563, 0.3523
```

因此，“证据面板每条都相同”不是所有运行路径的事实。核心错误是扩展/三路融合路径的最终门控仍固定使用 orig_max_conf，绕过了重排和选择后的分数。

受控复现中，先正常重排，再把五条选中证据的分数全部设为 0，得到：

```text
evidence_scores = [0, 0, 0, 0, 0]
response.confidence = 0.4641
refused = false
```

这是验证门控依赖关系的受控测试，不代表自然查询中的证据分数本来全是 0。

修复时应分别表示初始检索质量、每条证据相关性和最终可回答性，不能用一个最大值代替三种含义。最终拒答应消费实际选中的有效证据及路由动作。即使改为这些字段，也不能未经校准就称它们为正确概率。

## 6. 压缩与命名：确认

压缩后，远程模型/展示与本地抽取式生成读取不同文本的问题没有解决。普通样例已经复现：回答文本不变，展示证据被压缩，代理分数从 1.0 降至 0.747。字符比例放在 stage_timings_ms 中也混淆了单位。应让生成、引用、展示及评测共用同一份有效上下文，并把压缩统计单独存放。

建议采用与当前实现一致的名字：

| 当前名称 | 更准确的名称或说明 |
| --- | --- |
| LightRAGEntityGraph | EntityCooccurrenceGraph；受图检索启发的词项/技术编号共现图 |
| QueryExpanderHyDE | RuleBasedQueryExpander；静态领域词典扩展，不生成假设文档 |
| CRAGEvaluator | HeuristicRetrievalRouter，若继续保留现有阈值规则实现 |
| AutoRAGTuner | RRFGridSearch，若范围继续限于五组 RRF 参数搜索 |

方法来源可以保留在文档中，但不要把启发式实现写成官方框架集成或完整论文复现。历史审计快照保留当时名称；如后续实际重命名，需要同步导入、测试、API 文档、报告标签及必要的兼容迁移。

## 对外描述与后续验收

现阶段应将“新旗舰满分证明复杂方法有效”撤回，改为：“在同源合成基准上，规则扩展提高了检索指标；独立泛化能力尚未验证。”

先修正路由、置信度和证据一致性，并补上述反例回归；同时建立开发/测试隔离和规则来源记录。完成后冻结配置，再进行新的独立测试。当前成绩不能通过更名或重划旧数据自动恢复为独立测试成绩。
