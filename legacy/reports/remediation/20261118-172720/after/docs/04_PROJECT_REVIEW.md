# RAG 项目学习、求职与 Freelance 适用性审查

> 这是实施前的基线审查。修复后的状态、测试证据和未完成事项见 [实施审计报告](05_IMPLEMENTATION_AUDIT.md)。

审查日期：2026-11-18。范围：当前本地源码、数据、报告、部署文件，以及本地离线测试。本次未验证云端模型调用、真实 HTTP 大规模压测、Docker/Kubernetes 部署或浏览器渲染；没有修改业务代码。

## 结论

这个项目可以帮助学习 RAG，已有足够的主题广度作为作品集基础。当前最准确的定位是：**可运行的离线 RAG 检索与评估实验工作台，附带高并发机制实验和生产架构参考**。

目前证据不足以把它描述成“已交付的企业级 10,000 并发 RAG 平台”。求职方面，适合用于展示检索、实验设计和工程取舍；Freelance 方面，适合作为技术原型和方案演示基础，尚缺客户文档接入、可信回答评估及可运维交付闭环。

以上是针对当前仓库的技术判断，不是录用、获客或报价保证。无需为了学习或普通客户 MVP 先实现 10,000 并发。

## 已验证的内容

- 使用项目 `.venv/bin/python` 运行现有完整测试：**10 passed in 5.07s**，包括消融实验和进程内 10,000 请求测试。
- 测试期间强制使用 `local` 模式，临时目录位于项目内；测试生成的已有报告文件已恢复到测试前内容。
- `.venv` 和解释器基目录分别位于 `/Volumes/Data/Projects/Rag/.venv`、`/Volumes/Data/uv/python/...`。语料和报告默认位于项目目录。
- 额外通过小型脚本复现了语义缓存淘汰错误、缓存保留原始 PII，以及 faithfulness 无法识别事实关系颠倒的问题。
- 纯中文问题“什么是混合检索？为什么需要重排？”被当前默认管线拒答，confidence 为 0；当前 tokenizer、语料和 embedding 主要面向英文，不能据此宣传中文或多语言能力。

测试通过说明当前测试覆盖的行为成立，并不能替代生产环境和真实客户数据验证。

## 学习价值与边界

| 学习主题 | 现有实现 | 需要补充的知识或实践 |
| --- | --- | --- |
| 分块 | 固定窗口、Markdown、语义断点、父子分块 | token 长度预算、真实长文档、表格与 PDF 解析；当前主要按字符切分 |
| 检索 | TF-IDF + SVD 稠密向量、BM25、RRF | 预训练 embedding、真实向量数据库、领域外与多语言表现 |
| 重排 | 手工设计的词项覆盖、编号、bigram 等特征 | 真正神经 cross-encoder 的效果和延迟对照 |
| 评估 | Recall、MRR、NDCG、关键词覆盖、bootstrap | 独立测试集、证据片段标注、回答正确性、人工评审和失败分析 |
| 性能机制 | L1/L2 缓存、singleflight、限流、信号量、熔断 | HTTP/真实模型压测、持续负载、多进程共享状态、资源与费用记录 |
| 客户交付 | FastAPI、SSE 接口、演示页面、部署参考 | 文档导入/更新/删除、持久化、身份权限、运维手册与验收 |

建议先读 `data_gen.py → chunking.py → embeddings.py → retrieval.py → reranker.py → pipeline.py → evaluation.py`。初学时先关闭缓存跑通检索和回答，再研究缓存，否则缓存会掩盖修改后的实际行为。

每学一个模块，保留一组“原始问题、召回证据、回答、失败原因、修改前后指标”。能解释失败原因并独立完成一次改进，比背诵架构文档更能证明掌握了 RAG。

学习路线图还需校准：当前查询 API 和 Playground 没有提供 `chunking_strategy` 切换字段；对比分块需修改配置并重建管线。六组实验同时改变了多项设置，适合架构比较；若要判断某个因素的独立贡献，还需控制其他条件。

## 主要发现

### 1. “10,000 并发”的证据范围被扩大了

证据：`src/rag_platform/benchmark.py:109`、`:153`、`:158`；`pipeline.py:406`。

测试直接通过 `asyncio.gather` 调用同一进程中的 `pipeline.query`。默认是本地抽取式回答，模拟 LLM 等待只有 2ms；没有经过 HTTP、TLS、负载均衡、真实模型服务或跨节点数据库。

35% 热查询和 30% 语义查询比例由脚本设置；语义查询还预先筛选出达到缓存阈值的改写。这可以检验缓存机制，但 `74.96%` 卸载率是这套构造负载下的结果，不能当作真实客户流量观测。

成功条件主要是未限流且有回答或拒答，不代表回答正确。报告中的微秒级 P50 受本地缓存命中占比影响，不能作为云端完整 RAG 响应延迟。

可以表述为：“完成单进程、预热缓存及模拟模型延迟条件下的 10,000 协程请求实验。”

### 2. 默认模型与生产组件的实现深度有限

证据：`embeddings.py:27`、`pipeline.py:230`、`reranker.py:20`、`retrieval.py:65`、`cache.py`。

- embedding 是本地拟合的 TF-IDF + TruncatedSVD，可以用于理解向量检索，但不是预训练语义 embedding 模型。
- `CrossFeatureReranker` 是人工加权特征重排器，不是神经 cross-encoder。
- `CloudEmbeddingAdapter` 有定义，但没有接入主 pipeline；切换远程 LLM 不会自动切换 embedding。
- Redis/Qdrant 地址出现在部署文件，应用实际检索、缓存和 singleflight 仍在进程内。多个 worker/pod 不共享这些状态。
- SSE 在完整 `query()` 返回后才把已有回答拆成片段发送，尚未接入模型逐 token 生成流。

这些简化有教学价值，但应在 README 和面试中明确。

### 3. Faithfulness=1.0 不等于回答正确，也不等于标准 RAGAS 评估

证据：`pipeline.py:115`、`:139`；`evaluation.py:124`。

当前 faithfulness 计算回答词项在上下文中的覆盖率；默认回答又是从上下文中抽取句子，因此接近满分并不意外。额外复现：

```text
上下文：Alice paid Bob 100 dollars.
回答：  Bob paid Alice 100 dollars.
当前 faithfulness：1.0
```

该指标无法判断付款方向是否正确。标准 RAGAS Faithfulness 关注回答中的事实声明能否由检索上下文支持，定义不同：https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/

现有报告已经提示回答质量不足：旗舰配置的 conceptual_semantic 关键词覆盖率为 **0.208**，multi_hop 为 **0.425**。关键词覆盖也不是完整的正确性指标，但足以说明需要逐题检查回答，而不能只看 Recall@5=0.971 和 Faithfulness=1.0。

另外，引用列表会补入选中证据的文档 ID，不能据此保证每条引用都支持答案中的具体声明。

### 4. 评估集适合教学，尚不足以证明真实场景泛化

证据：`data_gen.py`、`evaluation.py:177`、`:291`、`reports/ablation_report.md`。

65 篇文档和 40 组 QA 在同一个生成模块中构造，未见独立锁定的开发/测试划分；不可回答样本只有 6 个。6/6 拒答不能泛化为真实攻击防护率 100%。

bootstrap 不能消除测试集选择、反复调参和数据代表性问题。接近 0.05 的数值不宜宣传为系统普遍优越的证明。

对 DS 面试更有价值的结果是：当前报告中，**BM25 的 NDCG@5=0.940，高于旗舰的 0.936**；旗舰 Recall@5 从 BM25 的 0.956 提高到 0.971，而报告平均延迟约从 0.48ms 增至 2.00ms。应讨论业务是否值得为这点召回增益支付复杂度和延迟，而不是默认最复杂方案最好。

### 5. 语义缓存淘汰存在可复现的跨配置错答

证据：`cache.py` 中 `L2SemanticCache.set` 与 `_matrix_by_scope`。

当缓存满时，`_entries.pop(0)` 会改变剩余所有条目的数组索引，但代码只重建被淘汰条目和新条目所属 scope 的索引。其他 scope 的旧索引可能指向错误 payload。

复现：容量设为 2，依次插入 `scope_A/A_old`、`scope_B/B_expected`、`scope_A/A_new`，再查询 B，返回的是 **A_new**。

当前 scope 表示检索模式、重排开关、top_k 和 domain 等配置；这会导致错误回答或错误的 domain 结果。系统目前没有实现租户隔离，不能把 domain 过滤等同于租户权限。

### 6. “缓存前 PII 脱敏”没有完全成立

证据：`pipeline.py:456`、`:476`、`:614`。

检索确实使用脱敏后的查询，但 response 的 `query` 保存 `raw_query`，之后整个 response 写入缓存。

额外脚本确认：输入 `alice@example.com` 后，`sanitized_query` 已脱敏，但 L1 缓存对象中的 `query` 仍包含该原始邮箱。因此不能宣传敏感信息已在缓存前完全去除。

此外，当前只有少量英文 prompt injection 正则，没有账号认证、文档级 ACL、租户范围检索和租户范围缓存。企业数据交付需要明确这些边界；OWASP 对 RAG 向量存储建议细粒度权限和数据隔离：https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/

### 7. 部署配置与磁盘位置需要区分“模板”和“已验证”

证据：`deploy/docker-compose.yml`、`deploy/k8s-production-10k.yaml`、`.env.example`、`config.py`。

Compose 可以作为参考拓扑，但服务代码没有接入其中的 Redis/Qdrant，Prometheus 也未见应用指标采集接线。Kubernetes 文件包含 Deployment/HPA/PDB，但未提供完整的应用镜像构建、Service/Ingress、模型密钥注入及依赖服务部署；不能称为已验收生产部署。

`.env.example` 是模板，当前代码未见自动加载它。仅编辑 `.env` 后直接执行 README 中的 uvicorn 命令，不能保证模式和缓存环境变量生效；需要显式加载或导出环境变量。

项目的 venv、Python 解释器、数据、报告路径确实位于 Data 盘。但“所有缓存和临时文件绝不使用系统盘”没有被当前启动流程强制保证，Docker 镜像和虚拟磁盘的位置也未验证。应缩小这项声明的范围。

## 推荐的后续 scope

### 优先级 0：修正可信度和明显错误

1. 修复语义缓存淘汰索引，并增加多 scope、过期、满容量测试。
2. 缓存只保存可共享的脱敏结果；补上原始 PII 不进入缓存的验证。
3. 把当前 faithfulness 更名为 lexical grounding proxy，并明确拒答满分的计算约定。
4. 修改 README 和面试 playbook：区分离线实现、模拟实验、架构设想和已实测部署，不直接使用“企业客户要求”“已解决注入漏洞”等未经证实的项目经历。
5. 显式提供环境加载和 Data 盘临时/缓存路径设置方式。

### 优先级 1：完成一个可信的业务 RAG 案例

选择一个范围清楚、可公开演示的领域，例如 SaaS 产品文档助手或内部技术支持知识库。

- 接入合法可用的真实文档，保留来源、版本和页码/章节信息。
- 实现导入、更新、删除、索引持久化，以及相应缓存失效。
- 接入一种预训练 embedding 和一种真实 LLM，并让演示明确显示模型、降级和缓存状态。
- 准备人工核对的开发集与独立测试集。可以先从约 100–200 个问题开始，按错误码、改写、多文档、无答案和版本冲突分组；这是实施建议，不是可靠性的样本数保证。
- 增加回答正确性、声明级引用支持、错误拒答和错误缓存命中评估，并展示具体失败例子。
- 在同一数据与条件下比较 BM25、预训练 dense、hybrid 和神经 reranker。
- 记录每问成本、P95 延迟，以及领域相关的收益指标，例如人工找资料所需时间。

达到这个阶段，项目就更适合 DS/Applied AI 面试，也能支持边界清楚的 Freelance PoC 或小型 MVP 演示。

### 优先级 2：按客户需求补交付能力

- 有私有数据或多个用户时，实现身份认证、检索前权限过滤和相应缓存隔离。
- 完成可复现构建、部署、监控、备份恢复、错误处理和交接文档。
- 用真实 HTTP 客户端测持续负载、冷/热缓存、错误率、尾延迟及资源占用；区分并发用户、同时在途请求和 RPS。现有 Locust 脚本可以作为起点：https://docs.locust.io/en/stable/what-is-locust.html
- 只有业务确实需要且经过预算和容量验证后，再扩展到 Redis/Qdrant 多节点和 10,000 并发目标。

验收应由双方约定的业务数据、质量门槛、并发负载、成本和部署边界决定，不能套用当前合成数据的指标或 playbook 的报价。

## 当前可以诚实使用的简历表述

> 构建可运行的 RAG 检索与评估工作台，实现四类分块、BM25/向量混合检索、RRF、特征重排及六组架构对照；在 65 篇合成文档、40 个问题上评估检索与回答指标，并实现缓存、请求合并和单进程 10,000 协程负载实验。

面试时主动说明合成数据、本地 SVD embedding、抽取式生成和模拟压测的限制。进一步修复本次发现的问题、加入真实文档并重做独立评估，会比继续增加架构名词更有说服力。
