## 优先处理的发现

### P1：CRAG 的 INCORRECT 状态没有落实为文档承诺的拒答动作

位置：快照 `pipeline.py:448`、`:515`、`:554`；`awesome_rag.py:243`。

复现查询为一个有效控制编号加八个词表外测试词。得到：

```text
crag_status = INCORRECT
refused = false
confidence = 0.505
citations = [SEC-COMP-001, CLOUD-ARCH-010, CLOUD-ARCH-004]
```

分类器因词表覆盖度判定 INCORRECT，最终回答分支却只看 selected 和 confidence，没有执行对应的拒答动作。因此指南中“INCORRECT 直接拒答”的契约不成立。这个反例证明路由状态与动作不一致，并不直接证明该条答案的事实一定错误。

修复方向：将评估结果转换为明确的执行动作，并由主管线统一执行。增加 INCORRECT、AMBIGUOUS、CORRECT 的端到端状态测试，不能只检查完全 OOV 的单个样例。

### P1：上下文压缩与默认抽取式回答使用了不同证据

位置：快照 `pipeline.py:526`、`:573`、`:577`。

真实执行当前压缩器，询问 `ERR_QDRANT_5032` 的含义与恢复方式：

| 项目 | 未压缩 | 开启压缩 |
| --- | ---: | ---: |
| 回答文本 | 与右侧完全相同 | 与左侧完全相同 |
| lexical grounding proxy | 1.0000 | 0.7470 |
| 上下文字符比例 | — | 0.4582 |

原因是展示和远程模型使用压缩后的 `ChunkEvidence.parent_text`，本地抽取式生成仍从原始 `selected` candidates 读取全文。回答会包含已经从展示证据中去掉的内容，指标和用户看到的依据随之失配。

修复方向：压缩完成后，让本地生成、远程生成、引用和评估使用同一组有效上下文，保留原始内容只用于独立的来源审计。压缩测试应验证回答支持关系和关键限制条件，而不只是长度变短。

另外，当前 ratio 是字符数比例，不是 tokenizer 测得的 token 比例；它不应直接作为真实模型 token 节省的测量值，也不宜混入毫秒计时字段而不说明单位。

### P1：调参器与主管线的权重/执行流程不一致

位置：快照 `awesome_rag.py:345`、`:362`；`pipeline.py:489`。

将配置设为 dense=0.9、sparse=0.1，并启用图检索，主管线实际传给三路融合的是：

```text
dense_weight = 0.45
sparse_weight = 0.35
graph_weight = 0.20
```

有 graph hits 时主管线硬编码上述权重；RAGConfig 也没有 graph_weight 字段。因此调参器枚举出的多种参数，不能统一通过相同配置结构在正式路径中重现。

调参器还总是扩展查询，跳过主管线的覆盖度/CRAG 条件、拒答和缓存策略。其分数是另一套检索流程的选择分数，不等于部署这组参数后的完整 RAG 质量。

当前接口只返回建议参数，没有自动应用或持久化。返回建议本身可以是合理设计，但必须明确说明，并提供同流程复核方式。应让服务、评估和调参共用检索/重排实现，记录开发集身份、输入哈希、全部参数与独立测试结果。

### P2：没有可评估问题时，调参接口返回 500

位置：快照 `awesome_rag.py:404`。

空 QA 或全部不可回答的 QA 会让 answerable 为空，随后除以零。已复现 `ZeroDivisionError`，以及 `POST /api/v1/autorag/tune` 返回 500。应提前返回明确的数据不足错误，不把它当作服务内部故障。

## 实现范围与开关行为

| 新增项 | 核对结果 |
| --- | --- |
| ContextualHeaderEnricher | 类可单独运行，但没有在主管线构建索引时调用；281 个索引块的 contextual_header 标记均为 0。测试仅单独调用 helper，未证明主索引使用了它。 |
| QueryExpanderHyDE | 是手写领域词典扩展，没有生成假设文档或编码假设文档。Pseudo-HyDE 可以作为灵感说明，技术名称宜优先写“领域词典查询扩展”。 |
| LightRAGEntityGraph | 实际为词项/技术编号的共现图及一跳传播，没有接入官方 LightRAG 框架。正则 IGNORECASE 使普通英文词也成为实体，`the and ordinary prose` 四个词全部入图。 |
| CRAGEvaluator | 是未校准阈值驱动的启发式路由，没有论文中的完整检索评估与知识纠正流程。 |
| ContextualCompressor | 是词项覆盖加位置奖励的抽取过滤器；远程生成已使用其输出，本地生成存在上述接入错误。 |
| AutoRAGTuner | 能执行五组网格搜索并返回最佳建议；不是官方 AutoRAG 框架集成，也没有完整的开发/独立测试闭环。 |

这些简化作为教学实现有价值。方法边界可对照 [HyDE 原论文](https://arxiv.org/abs/2212.10496)、[CRAG 原论文](https://arxiv.org/abs/2401.15884)、[LightRAG 官方仓库](https://github.com/HKUDS/LightRAG) 和 [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)。静态元数据头也不同于为每个块生成针对性解释上下文的完整方法。

### P2：关闭图检索仍然支付建图成本

`pipeline.py:295` 无条件初始化图。当前 65 篇文档、281 块的单次观察：2,249 个词项节点、327,014 个有向邻接项，图构建约 121ms。该数字仅适用于此样本，不是容量外推。

图构建对每块实体集合做两层循环。普通词和停用词入图还会增加无意义关联。建议在明确启用图检索或运行图调参时延迟构建，并区分技术实体与普通词项、限制邻接规模。

### P2：同一管线热切换功能时，缓存可能返回旧实验结果

复现：先在 CRAG 关闭时查询并缓存，再把同一 config.enable_crag 设为 True。相同问题命中 L1，状态仍是 DISABLED；关闭缓存重问则为 CORRECT。

这是程序内热切换场景。当前 HTTP/UI 没有这些功能开关，因此不能夸大成已有 UI 必然串结果；但学习脚本应关闭缓存或重建管线，未来若支持动态开关，应将影响答案的配置版本纳入缓存范围。

### 默认运行与学习入口

四个新增开关默认均为 False。第七组实验启用 CRAG、图和查询扩展；上下文压缩不在该组的 spec 中。当前默认启动和查询页面不能直接比较全部新增选项，真实 Python 资料评估脚本也仍只比较原有四种检索组合。

指南应给出明确的启用方式、实际运行参数和逐项实验，不把“存在 helper”写成“默认主管线已启用”。

## 效果复核

七组实验已在冻结源码上重新计算，新增组合的合成集结果可以复现：

| 配置 | Recall@5 | MRR | NDCG@5 | 关键词覆盖 |
| --- | ---: | ---: | ---: | ---: |
| 第 6 组 | 0.9706 | 0.9338 | 0.9362 | 0.4779 |
| 第 7 组 | 1.0000 | 1.0000 | 0.9917 | 0.5074 |

这是当前合成资料上的观察，不能说统计提升是假数据。但词典中的 `8-bit`、`vocabulary`、`statistically` 等触发词与现有题目紧密对应；没有独立资料和标签验证时，存在对当前题集过拟合的风险。检索指标提升也没有证明回答正确性已改善。

额外用已有 9 篇 Python 真实资料、13 道固定测试题比较原有第 6 组风格与开启三项新特性的组合：两者 Recall@5、MRR、NDCG@5 都是 1.000，关键词覆盖同为 0.3182。此集合过小且已饱和，不能判定新增方法普遍无效，也不能把合成提升外推到新领域。

下一步应增加同主题不同条件的干扰资料、未知改写、短查询、缺失证据、多跳和无答案样例，采用独立审核的开发/测试划分。对新组件逐项启停，并保持其他条件一致，明确增益、回归和延迟来自哪里。

## 建议下一批范围
