# 并发机制实验与容量规划边界

原文件名保留便于追溯。当前项目没有生产万并发验收记录。

## 当前实际实现

单个 FastAPI worker 内：脱敏/简单注入正则 → 限流 → L1 → 查询 embedding → L2 → singleflight → semaphore → 检索/重排 → 抽取式或远程生成。

缓存、限流、熔断和 singleflight 都在进程内。多个 worker 各自维护状态；Redis/Qdrant 尚未接入。

本地文档写入使用 POSIX 文件锁和原子替换。其他 worker 在后续请求检查语料变化并重建快照；已在途请求允许完成旧版本。这不是跨机器的强一致数据库。

## 单进程实验

`scripts/workbench synthetic --requests 10000` 创建 10,000 个协程请求。LLM 是本地抽取式回答并附加模拟等待；脚本不经过 HTTP。

35% L1、10% burst、30% 语义改写、25% cold 的输入比例由脚本构造。语义改写预筛选过向量相似度；加入编号/数字一致性约束后，实际命中层级可能不同。不能把该缓存比例当作真实客户流量。

延迟从协程开始执行计时，包含内部排队，不包含客户端网络和开始前调度等待。完成率不评价答案正确性；P50/P95/P99 应一起阅读。

## 真实 HTTP 复核

在独立终端启动服务后运行：

```bash
scripts/workbench start
# 另一终端
scripts/workbench http-benchmark --requests 200 --concurrency 10
```

客户端报告连接并发上限、HTTP 状态码、RPS 和 P50/P95/P99。延迟从取得客户端槽位开始，不含槽位前等待；这是有限请求的闭环负载，不是长时间容量验收。

本次沙箱不允许监听 localhost，因此真实网络测试未执行成功；ASGITransport 接口测试也不能替代它。

扩大验证时，需要确定硬件、输入/输出长度、真实模型、缓存比例、到达率、持续时长、资源占用、费用和错误预算，再逐步增加负载。

## Little's Law

`L = λ × W` 中 L 是平均在途请求数，λ 是稳态吞吐，W 是平均停留时间；L 不是简单的注册用户或在线用户数量。

在固定吞吐下，降低 W 可以减少平均在途请求及冷生成槽位。若把 L 固定并用更小 W 反推更高 λ，则比较条件已改变，不能据此直接声称同等流量的算力节省。

缓存复用还必须满足权限、版本、编号和数值约束。命中率只有在答案有效的前提下才有意义。

## 未来扩展的验收前提

Redis 跨 worker 缓存/请求合并、Qdrant 持久向量索引、神经 reranker、真实模型流式返回、分布式追踪、持久审计、身份 ACL 和多节点容灾仍需独立实现和验证。
